From monitor to accountable pool operator

The project already performs meaningful autonomous work. The next step is not a chat box: it is a visible, evidence-backed action loop that can recommend, request approval for, execute, and learn from maintenance decisions.

Current reality

Grounding Context

Already autonomous

runner.py polls, fast-confirms elevated readings, warns before a threshold, persists alert state, auto-recalibrates after a cleaning signature, and can perform an emergency shutoff.

Dashboard is observational

index.html derives forecasts and cost client-side from static CSV/JSON files. Its only recorded user action—manual cleaning—is stored only in browser localStorage.

Learning is narrow

trend.py uses a seven-day least-squares extrapolation; data_logger.py retains 30 days. There is no diagnosis confidence, action outcome, or context dataset.

Safety needs a product surface

Emergency shutoff is enabled and directly invokes pump controls after confirmed critical readings. The audit log records the stop, but the user cannot set or inspect an explicit approval policy from the dashboard.

Recommendation: make the dashboard the agent’s shared operational surface: one durable record of facts, hypotheses, pending decisions, approved actions, and observed outcomes. Keep deterministic safety rules as the authority; use language models only for explanation and bounded suggestions after the evidence layer is in place.

I1

Turn the hero into a “Do this next” action loop

Operator experience
Confidence · 92%Complexity · Medium

Replace the status-only hero with one current operational card: condition, recommended action, urgency, evidence, expected benefit, and a bounded response. Examples: “Inspect skimmer within 4 hours,” “Confirm filter cleaned,” “Watch until 2:15 PM,” or “Emergency stop already executed.” It should always name the next owner and show the card’s lifecycle: proposed, awaiting approval, done, expired, or superseded.

Basis
direct: the dashboard already forecasts cleaning and renders alerts, while notifications are one-way and manual cleanings are browser-only. external: Home Assistant documents notification actions that return an event to the automation, demonstrating a practical request/response loop for home operations.
Rationale
The project already knows enough to detect and forecast. Framing that knowledge as one actionable commitment turns passive observability into supervised autonomy without asking the user to interpret charts first.
Downsides
Requires a small command endpoint and disciplined action states; a vague “AI recommendation” would be worse than today’s direct alert.
I2

Establish a durable operating state and event ledger

Operational state
Confidence · 90%Complexity · Medium

Create a single structured record for readings, model outputs, recommendations, user responses, actuator commands, delivery attempts, and outcomes. The static dashboard, push notification flow, and any future agent should all read the same facts and append to the same ledger; the dashboard must stop reconstructing critical state from CSV plus browser storage.

Basis
direct: runtime state is split across metrics.csv, several JSON files, state.json, shutoff.log, and browser localStorage. reasoned: a system cannot resume a pending approval or learn from a manual cleaning if those facts are siloed or client-local.
Rationale
This is the enabling simplification. It gives the existing deterministic monitor and future agentic features a shared truth, durable pending work, and an inspectable history.
Downsides
Introduces a migration and retention decision. Start with SQLite or append-only JSONL behind a repository interface, not a full cloud platform.
I3

Show an evidence-backed diagnosis, not only a severity

Diagnosis & uncertainty
Confidence · 88%Complexity · Medium

For every abnormal condition, create a diagnosis card that separates observed facts from hypotheses: “likely dirty filter,” “possible priming transition,” “possible cloud telemetry fault,” or “possible bypass/drain profile.” Display confidence, competing explanations, the confirmation window, and the exact readings/rules that changed the recommendation. When confidence is low, choose “observe” or “ask for inspection,” never escalation by invented certainty.

Basis
direct: the engine already recognizes startup grace, contradictory RPM/flow telemetry, zero-flow streaks, and bypass-like profiles, but the dashboard does not expose those distinctions. reasoned: the same telemetry pattern can indicate blockage, a transient, or a data-quality issue, so severity alone is insufficient for safe action.
Rationale
Explanation makes the existing automation debuggable and lets the user calibrate trust. It is also the prerequisite for sensible natural-language answers later.
Downsides
Needs careful copy and explicit confidence rules; do not imply sensor-grade certainty from an indirect pressure proxy.
I4

Make authority explicit with a permission ladder

Action authority
Confidence · 87%Complexity · Medium

Expose an editable policy that classifies actions as observe-only, notify, recommend-and-await-confirmation, delayed emergency action, or automatic. Require an action record with policy version, inputs, reason, expiry, user approval/rejection, and result. Keep pump shutoff in the most constrained tier and make policy changes visible in the dashboard’s decision history.

Basis
direct: runner.py can already turn off the pump and disable its status switch after critical confirmation; the configuration exposes only a boolean switch and delay. external: agent human-in-the-loop patterns preserve pending approvals durably and resume after an explicit approve/reject decision.
Rationale
Autonomy becomes safer when its boundaries are understandable and adjustable. This converts a hard-coded emergency behavior into a deliberate operational contract.
Downsides
More policy states can confuse a household user. Offer opinionated presets (“conservative,” “protect equipment,” “hands-off”) instead of a dense rule builder.
I5

Close the maintenance loop with outcome learning

Outcome learning
Confidence · 85%Complexity · Medium

When a user says “cleaned,” “skimmer emptied,” “ignored,” or “not a filter issue,” persist the action as a structured outcome and schedule post-action checks. Compare the next stable readings with the prediction, then mark the recommendation as helped, neutral, or contradicted. Use those outcomes to tune baseline confidence, alert timing, and future explanation—not to rewrite safety thresholds automatically without policy.

Basis
direct: auto-recalibration recognizes only one cleaning signature; dashboard manual-cleaning records live in browser storage and cannot inform the runner. reasoned: a maintenance recommendation can only improve if the system retains what was done and compares the expected versus observed recovery.
Rationale
This is the largest jump from automated monitoring to an agent that gets better in the context of one pool.
Downsides
Outcomes will be sparse and noisy. Treat them as evidence for confidence and review prompts before using them to alter protective behavior.
I6

Fuse maintenance and environmental context before forecasting

Diagnosis & uncertainty
Confidence · 76%Complexity · Medium

Let the monitor collect a small, explicit context stream: pump schedule changes, manual cleaning, basket service, cover status, and local rain/wind or storm events. Use it first to explain changes and prioritize inspections; only later, once enough outcome history exists, use it to adjust forecast intervals or proactive reminders.

Basis
direct: the README identifies storms, leaves, startup spikes, and water level as different causes of abnormal behavior, but the model sees only pump telemetry. reasoned: adding causal context reduces false confidence in a single ratio and makes recommendations more specific than “filter may be clogged.”
Rationale
It preserves the project’s simple proxy while giving the diagnosis layer the context needed to distinguish routine fouling from an event-driven incident.
Downsides
External weather integrations can create noise and dependency risk. Start with manually logged maintenance plus schedule changes; treat weather as optional enrichment.
I7

Add “Ask the monitor” only on top of the ledger and diagnosis

Operator experience
Confidence · 70%Complexity · High

After the shared ledger and diagnosis cards exist, add a constrained question surface for questions such as “Why did you warn me?”, “What changed after the last cleaning?”, and “What should I inspect first?” Responses must cite telemetry, action records, and policy; the agent may create a recommendation but cannot change controls except through the permission ladder.

Basis
direct: the dashboard currently exposes charts and technical details but no path from a question to the underlying historical evidence. reasoned: language is useful for translating a structured operational record, not for replacing it or deciding unsafe controls from raw prompt text.
Rationale
This makes the system feel conversational without making a model the source of truth. It is intentionally last because the first six ideas supply the evidence, action semantics, and safety boundary it needs.
Downsides
Costs, privacy, and hallucination risk. Do not ship this as an unconstrained general chatbot or use it as the alerting engine.
What did not clear the bar

Rejection Summary

IdeaReason rejected
Put a generic LLM chat box on the dashboard nowBelow the ambition floor: it would sit on fragmented data, cannot safely act, and would add a more polished way to ask uncertain questions rather than improving operations.
Replace deterministic thresholds with an LLM anomaly detectorBasis refuted by the safety context: the current rules provide confirmation and startup/bypass safeguards; an opaque model would weaken explainability before enough labeled outcomes exist.
Build a full Home Assistant integration firstInteresting distribution option, but it widens the product surface and duplicates the missing shared-state/action semantics rather than solving them.
Make a broad smart-pool platform for chemistry, lights, and heatingSubject replacement: it abandons the focused filter-protection problem before the existing monitor is a complete supervised agent.
Auto-adjust all thresholds after every apparent cleaningToo risky relative to evidence. The existing recalibrator is intentionally narrow; outcome learning should improve confidence and prompt review before it expands autonomous policy.
Store more than a year of raw CSV in the browserDuplicates the stronger durable ledger direction and is not a credible agent foundation by itself.
